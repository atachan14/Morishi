# v2 根・雨・成長の長期観測

基準HEAD3070485から、既存本体の再現可能な計測を実施。停止・隔離修正はローカルコミット0eed53e。ルールや調整値は変更しない。対象はecosystem-v2.htmlのrootモード。

## 条件

標準100体、半径2400、seed424/614。無操作と開始時3枚配置を比較。配置は左上側の100刻み格子を固定順で走査し、許可される最初の地点を採用。近接した集団配置であり、早期合体を起こす。分散配置や上手い人のプレイの代用ではない。

各3仮想日=43200ticks=4320シミュレーション秒。天気の仮想日付は1tick=6秒。昼夜は現仕様では手動であり、本計測の入力として7200ticksごとにsunlight1/0を切替。雨は既存seed/tick規則。6仮想時間ごとに状態・保存容量・CPUバッチ時間・ヒープを記録し、保存復元と復元後3ticksの一致を検査。

Node計測は直列、100ticksごと20ms休止、自分の計測プロセスをBelowNormalに設定。ww_ggや既存Vite・ユーザーブラウザには触れない。モデルを隔離し、本番localStorageを使わない。

## 見つかった停止と修正

seed424無操作のtick26572（2仮想日弱）でInvalid root plant。合体タンク容量7300に対し、water=7299.9999999999545、mix合計=7300.0000000999635。満水との差約4.5e-11を多数の土壌領域で分割加算し、水の加算は丸められる一方で細かい成分が加算され続け、許容差1e-7を越えていた。

満水の判定を容量に対する浮動小数点精度（32×Number.EPSILON）で行い、各植物への水・成分の加算は領域分を集計して一度に行う。ゲームの水量・成長・天気設定は変えていない。旧HEADの小再現では水量差0、栄養差2.27e-12を確認し、新しい回帰テストはこの不要吸水を拒否する。停止前の保存点tick25200から修正モデルで再開して停止時刻を通過。

別途、予報中の昼夜onclick直接呼び出しに本体変更の保護漏れを修正。通常操作ではボタンは無効化されていたが、他の操作と同様のガードを追加し、PC/SPの直接ハンドラー回帰で全モデル・全保存キーの不変を確認。

## 計測結果

初期吸水を別の1夜間tickで分離計測した。同じ標準配置で競合により単独時より取得が下がる根はseed424で16体、614で15体。最低取得率はそれぞれ92.1%、90.6%、3枚配置時は614で88.6%。最低取得量は0.3565/0.3259水毎tick（3.565/3.259毎シミュレーション秒）で、現行消費2/秒を上回る。共有領域の競合は実際にあるが、初期条件では不足を生じさせるほどではない。initial-competition.jsonに個体別の単独時上限と実取得を記録。

結果表はmeasurements.jsonの完了ケースに基づく。途中停止前の数値はfailure.json。seed424無操作はtick25200まで旧モデル、以降修正モデルであり、この行とGC有効化でtick28800から再開した614無操作のCPU時間は再開後区間のみ。他のケースは修正後の新規run。

ブラウザでは隔離headless Edgeで標準100体を約160秒観測。昼→夜→昼、停止保存・再読込・再生を含む。フレーム間隔95%点18.3～18.5ms、最大105.5ms（再読込後再生区間）。GC後ヒープは再読込前約17～18MB、イベントリスナー112→114後に横ばい。3日後の1体状態を別の隔離Edgeへ復元して60秒観測し、95%点18.2～18.3ms、最大68.9ms、GC後ヒープ約9～10MB。CPUはCDP TaskDuration/ScriptDurationとして保存。DOM数はGC前で一時的な破棄待ちノードを含む。

Nodeの前半のheap/RSSはGCを強制していない生値であり、保存復元比較で作る一時モデルを含む。後半は解放・GC後ヒープも追加した。GC前の生値だけで単調な増加や漏れを判定しない。ブラウザの短時間結果から長期メモリ漏れなしと断定しない。実機スマホは未確認。

## 成長後の同期時間送り

隔離Edgeで3日後の同じ満水保存点を使い、1倍の10秒送りは1433ms、8倍の80秒送りは8256msだった。満水で吸水可能量0の根も土壌接触を再計算していたため、接触計算の候補から除外した。水・成長・天気・合体設定は変更しない。3保存点×昼夜×16ticksで省略前0eed53eと全rootフィールドの厳密一致を確認し、全299tests・型検査・両buildを再実行して成功。

同じ操作は1倍451ms、8倍2089msへ短縮（8倍で約75%削減）。forwardの同期処理自体は残るため、約2秒の待ちと昼間の吸水計算には改善余地がある。次の性能候補は時間送りの分割実行と、接触・profile計算の再利用。長期4ケースは省略前0eed53eのデータであり、この最適化後に12仮想日全体を再実行したとは扱わない。

## 調整候補と次工程

まずsizePerWater単独の比較で、半日100→7～15体、3日1～2体への早い集約を緩める条件を計測する。合体後の消費は各個体2/秒のままなので、集約に伴い全体需要も急減し、貯水が余りやすい。成長量と合体頻度を先に分離し、雨・初期土壌水の変更はその後に単一条件ずつ比較する。

近接3枚配置の全滅はこの入力戦略の結果。分散配置・配置時刻・初期根/防御差を比較してから味方全般の弱さを判断する。今回のパラメータは固定し、仮の調整は適用していない。長い待機、人間の面白さ、実機スマホ、より長い実時間のメモリ観測は未確認。
